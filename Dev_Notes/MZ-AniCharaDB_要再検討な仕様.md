## 3. 完全重複カードの破棄タイミングと方式　✅ 確定

| 項目 | 決定内容 |
|------|--------|
| 即時破棄しない理由 | 停電等の異常終了時への備えのみ。原本はアーカイブ済みのため、データ保護上の猶予期間は不要 |
| 削除タイミング | dispatcher の終了フェーズで削除（ステータスログ記入・タスクマスターへの報告と同一フェーズ） |
| archiver との関係 | archiver は関与しない。dispatcher が自己完結して処理する |
| 復元の考え方 | 誤判定時はアーカイブから復元する前提。破棄待ちリスト自体に復元保護の役割はない |

## 4. 03b_merge 比較リストとマージUIフロー　✅ 確定

比較リストの構造・マージUIフロー・dispatcher改修方針・各種パスすべて確定。「ほぼ固まりつつある仕様」ドキュメントへの転記を忘れずに。

### 4-1. 比較リストの構造　✅ 確定

JSONの配列。1件1配列で、以下の4要素を固定順で格納する。

| インデックス | 内容 | 型 |
|------------|------|----|
| `[0]` | 重複発見日時 | 文字列（ISO8601） |
| `[1]` | 既存カード側のファイル名 | 文字列 |
| `[2]` | 新カード側のファイル名 | 文字列 |
| `[3]` | ペンディング回数 | 整数 |

並び順はペンディング回数の多い順。

```json
[
  ["2024-06-01T12:00:00Z", "existing_card_001.json", "new_card_001.json", 5],
  ["2024-06-02T15:30:00Z", "existing_card_002.json", "new_card_002.json", 3],
  ["2024-06-03T09:45:00Z", "existing_card_003.json", "new_card_003.json", 2]
]
```

### 4-2. マージ作業フロー（方針）

マージ作業は専用のマージUI（別途 PHP/UI）で行う。原則として目視チェック。

| ステップ | 主体 | 内容 |
|---------|------|------|
| ① ペア読み込み | マージUI | 比較リストからペンディング回数の多い順にペアを読み込み、既存カードと新着カードを対で表示 |
| ② キー選択 | 作業者 | 各キーについて採用する側を選択 |
| ③ 検討保留 | マージUI | 「検討保留」ボタン押下で当該ペアのペンディング値をインクリメントし、次のペアへ進む |
| ④ 新カード作成 | マージUI | 確定後、マージ済み新カードとして生成し `src/app/03b_merge/M_Confirmed/` へ配置 |
| ⑤ dispatcher への流し込み | dispatcher.php | 通常の `02_valid/Confirmed/` を読んだ後、マージ済みフォルダも読みに行く機能を追加（★要実装） |
| ⑥ 既存カードの退避 | dispatcher.php | 新カード作成が済んだものは `index.json` から当該行を削除し、実ファイルを OLD ディレクトリへ移動 |

### 4-3. 実装詳細メモ　✅ 確定

| 項目 | メモ |
|------|------|
| マージ済みフォルダのパス | `src/app/03b_merge/M_Confirmed/` で確定 |
| 比較リストのエントリ削除タイミング | マージUIが新カードを `M_Confirmed/` に書き出したタイミングで当該エントリを削除。dispatcher による OLD 退避を待たずに消してよい |
| OLD ディレクトリのパス | `app/mainDB_OLD/` で確定。JSON のまま配置 |
| OLD のzip化タイミング | 厳密なトリガー管理は不要。バラのJSONが溜まった状態と日時.zipが混在していてよい。定期的にまとめられていれば十分 |
| dispatcher への機能追加の実装方針 | 同一ルーティンで順番に処理。`02_valid/Confirmed/` を処理し終えたら続けて `03b_merge/M_Confirmed/` を読みに行く。空なら終了フェーズへ（`02_valid/Confirmed/` が空の場合も同じ挙動）。処理件数はそれぞれ `dispatcher_status.json` に記録する |
| ゲート追加 | `dispatch_merge` ゲートを新設。既存の `dispatch` とは独立して開閉できるようにする。ゲートリスト・`task_master.json`・`is_gate_open()` の対象に追加すること |
| 処理件数の記録 | `dispatcher_status.json` に各フォルダでの処理件数をそれぞれ書き出す |
| 処理件数のログ | `dispatcher_status.json` に記録。`02_valid/Confirmed/` 処理件数と `M_Confirmed/` 処理件数をそれぞれ書く |
| ペンディング回数のインクリメント主体 | マージUI（別途 PHP/UI）。「検討保留」ボタン押下時に当該ペアのペンディング値をインクリメントし、次のペアへ進む。dispatcher は関与しない |

## 5. content_hash のアルゴリズム　✅ 確定

| 項目 | 決定内容 |
|------|--------|
| アルゴリズム | MD5（SHA-256 より文字列が短く、index.json など人間が目視するリストでの視認性が高いため） |
| ハッシュ対象範囲 | `name` 以下の本文部分（`header` は除外）で確定。header を含めると `generated_at` 等の時刻差だけで別ハッシュになり、同一内容カードを重複と判定できなくなるため |
| JSON シリアライズ順序 | 転記順のズレによる別ハッシュ化は当面許容。名寄せ・重複いずれかのマージの際に順序が統一され自然に収束する想定 |

## 6. index.json の詳細構造

dispatcher.php が参照する `index.json` の暫定構造は以下だが、「indexer 実装時に確定」とされており未定。

```json
{ "作品名_キャラ名_枝番": "content_hash値", ... }
```

| 検討が必要な点 | 内容 |
|-------------|------|
| キー区切り文字 | アンダースコアで作品名やキャラ名にも `_` が含まれる場合の衝突対策 |
| 複数エントリの管理 | 同一作品・キャラで枝番違いが増えた場合の一覧取得方法 |
| インデックスの更新タイミング | indexer_add / indexer_rebuild のどちらがいつ書き込むか |
| 大規模時のパフォーマンス | JSON 全読み込みがボトルネックにならないか |

→ indexer 実装開始前に構造を確定し、dispatcher との整合性を検証すること。

## 7. product ブロックのキー名寄せ

現在 `product` ブロックのキーは日本語・英語の混在を許容しているが、「将来的に名寄せマスターで英語キーに統一予定」とされており、過渡期の扱いが曖昧。

| 論点 | 現状 |
|------|------|
| 日英混在の許容範囲 | 過渡期は許容。ただし「過渡期」の終了条件が未定 |
| 名寄せマスターの整備時期 | 未定 |
| スペルミスの扱い（`voise` → `voice`） | normalizer では処理しない。名寄せフェーズで人手判断 |
| 表記ゆれの自動検出方法 | 未定（fuzzy match 等の導入検討が必要か） |

→ 名寄せマスターの設計・整備スケジュールを別途計画すること。

## 8. extended ブロックのスケール統一

`extended` の値スケールは「原則 0〜10」だが、作品固有のスケールを使う場合は「コメントか別途メモで明示」とされており機械的に扱えない。

- スケール情報をJSONに埋め込む場合のフィールド設計が未定
- 名寄せマスターでの対応表管理も「将来予定」止まり

→ 異スケールの値を比較・集計する要件が生じる前に設計を決定すること。
