## 1. スキーマ・ヘッダー仕様

スキーマバージョン文字列・ヘッダーブロックの構造は確定済み。運用上のルールも含めて合意されている。

### 1-1. スキーマバージョン文字列

| 項目 | 内容 |
|------|------|
| 現行バージョン | `MiZu_Character_Profile_v1.2602.01` |
| 既知バージョン（normalizer対応済） | `v1.2602.01` / `v1.2508.02` |
| 格納キー | `header.schema`（処理必須） |
| 不一致時の動作 | `02_valid/error/` へ移動して処理中断 |

### 1-2. headerブロック 各フィールドの役割

| フィールド | ルール・備考 |
|-----------|------------|
| `schema` | 固定文字列。手書き・カードメーカー問わず必須 |
| `uuid` | アップローダーJS側で付与。手書き時は `null` |
| `sid` | アップローダー側で付与。手書き時は `null` |
| `content_hash` | normalizer.php が付与。手書き時は `null` |
| `generated_at` | ISO8601（UTC）。カード生成日時。処理必須 |
| `first_registered` | マージ時は旧カードの値を引き継ぐ。管理必須 |
| `last_updated` | 更新のたびに書き換え。管理必須 |

## 2. name / work【処理必須】

両フィールドとも空文字・null 不可。正式表記は公式準拠を推奨し、略称や通称は `tags` で補完する。

## 3. JSONカード構造・各ブロック

### 3-1. 必須レベル定義

| レベル | 意味 |
|--------|------|
| **処理必須** | 欠けるとインポート処理が停止する |
| **管理必須** | 欠けると運用上の追跡が困難になる |
| **推奨** | あると品質・検索性が向上する |
| **任意** | 作品・キャラによって入れる |

### 3-2. トップレベル構造サマリー

| キー | 必須レベル / 補足 |
|------|----------------|
| `header` | 処理必須 |
| `name` | 処理必須 |
| `work` | 処理必須 |
| `profile` | 推奨 |
| `product` | 推奨（キーは自由記述・日英混在許容） |
| `tags` | 推奨（`affiliations` / `character_tags`） |
| `rating` | 推奨（1〜5整数、基本3項目） |
| `personality_parameters` | 推奨（基本5軸、values合計10.0） |
| `extended` | 任意（作品固有パラメーター） |
| `assets` | 任意・将来用（現時点は空配列固定） |
| `comments` | 推奨（`intro` / `evaluation`） |

### 3-3. personality_parameters ルール

- キーは `軸1` / `軸2` … の連番
- `labels` は必ず2要素（左が基準側）
- `values` は必ず2要素、合計が **10.0** であること
- `anchor` = 補正基準側インデックス（通常 `0`）
- 未評価時デフォルト：`[5.0, 5.0]`
- 基本5軸：社交的/内向的・行動的/慎重・直感的/論理的・情緒的/理性的・楽観的/悲観的

### 3-4. profile.birthday の型

`value` は文字列型 `"yyyy/mm/dd"` 形式。ISO日付型（Date型）には変換しない。

## 5. normalizer.php の処理仕様

`01a_import_norm/~temp_[SID]/` のJSONを1枚ずつ読み取り、正規化・検証のうえ `02_valid/` に出力する。

### 5-1. 処理順序

1. スキーマチェック（`header.schema` の確認）
2. JSON正規化：複製転記方式（破損JSONを直接修復せず、既知フィールドを定義順に新オブジェクトへ転記）
3. content_hash の生成・付与（MD5、対象は `name` 以下の本文部分・header は除外）
4. 出力：成功 → `02_valid/Confirmed/` / 失敗 → `02_valid/error/`

### 5-2. 複製転記方式で自動排除されるもの

| 問題 | 処理 |
|------|------|
| 値末尾の余分な `"` | 転記時に自動除去 |
| 値先頭・末尾のスペース | トリムで除去 |
| カンマ抜け | 転記方式のため自動補完 |
| キー末尾の余分な `_` | 転記時に除去 |
| タブ・スペース混在インデント | 転記方式で自動解消 |

### 5-3. normalizer が処理しないもの（名寄せフェーズへ）

- キーの日英混在（`"アニメ制作"` と `"studio"` 等）
- スペルミス（`voise` → `voice` 等）
- 表記ゆれ・意味の同一性判断
- 値が同一なのにキーが分かれているケースの統合判断

### 5-4. エラー理由の記録方式

| 項目 | 決定内容 |
|------|--------|
| 記録先 | `src/app/normalizer_error.log` への追記 |
| フォーマット | 1件1行（ファイル名＋エラー理由） |
| エラーファイル自体 | `02_valid/error/` へ移動するのみ。ファイル名・中身は変更しない |

## 6. dispatcher.php の振り分けロジック

`02_valid/Confirmed/` の正規化済みカードを1枚ずつ読み取り、`mainDB/index.json` との照合結果に応じて振り分ける。

### 6-1. 判定フロー

| 照合結果 | 振り分け先 | 備考 |
|---------|-----------|------|
| 該当なし（新規） | `mainDB/registercache/` | indexer_add.php が本体へ登録 |
| 該当あり＋content_hash 一致 | 破棄待ちリスト | dispatcher 終了フェーズで削除 |
| 該当あり＋content_hash 不一致 | `03b_merge/` | 人手マージ待ち |

### 6-2. 完全重複カードの破棄タイミング

| 項目 | 決定内容 |
|------|--------|
| 即時破棄しない理由 | 停電等の異常終了時への備えのみ。原本はアーカイブ済みのため猶予期間に保護上の意味はない |
| 削除タイミング | dispatcher の終了フェーズで削除（ステータスログ記入・タスクマスターへの報告と同一フェーズ） |
| archiver との関係 | archiver は関与しない。dispatcher が自己完結して処理する |
| 復元の考え方 | 誤判定時はアーカイブから復元する前提 |

### 6-3. index.json の照合キー（暫定）

```json
{ "作品名_キャラ名_枝番": "content_hash値", ... }
```

## 7. core.php・ゲート設計

### 7-1. core.php の役割

- cron から定期呼び出しされる監視係
- モジュールを上から順に呼び出し、終了コードで次へ進むか判断
- `flock()` で自身の多重起動を防ぐ

### 7-2. 終了コード規約（全モジュール共通）

| exit コード | 意味 |
|------------|------|
| `exit(0)` | 正常終了（処理完了・ゲート閉・対象ファイルなし、すべて含む） |
| `exit(1)` | 異常終了（処理中にエラーが発生した場合） |

### 7-3. ゲートの概念

ゲートは「自分が動いていいか」ではなく、**「下流が上流に汲み取りに来ていいか」** の許可フラグ。

| ゲート名 | 意味 |
|---------|------|
| `receive` | normalizer.php が import_Norm の成果物を汲み取りに行っていいか |
| `normalize` | dispatcher.php が normalizer の成果物を汲み取りに行っていいか |
| `dispatch` | 以降の振り分け処理を行っていいか |
| `archive` | archiver.php が動いていいか |
| `index_add` | indexer_add.php が動いていいか |
| `index_rebuild` | indexer_rebuild.php が動いていいか |
| `dispatch_merge` | `03b_merge/M_Confirmed/` からの読み出しを行っていいか。`dispatch` とは独立して開閉する |
| `build_statistics` | statistics系の親ゲート（子ゲートより優先） |

### 7-4. 標準運用モード別ゲート設定

| ゲート | 通常運用 | ベリファイ貯め置き |
|--------|---------|----------------|
| `receive` | true | true |
| `normalize` | true | true |
| `dispatch` | true | false |
| `dispatch_merge` | true | false |
| `archive` | true | true |
| `merge_return` | true | false |
| `index_add` | true | false |
| `index_rebuild` | false | false |

### 7-5. ゲートチェックの共通パターン

```php
require_once __DIR__ . '/api/config.php';
if (!is_gate_open('ゲート名')) { exit(0); }
// ===== 処理本体 =====
```

## 8. content_hash の仕様

| 項目 | 決定内容 |
|------|--------|
| アルゴリズム | MD5 |
| ハッシュ対象範囲 | `name` 以下の本文部分（`header` は除外）。header を含めると `generated_at` 等の時刻差だけで別ハッシュになり同一内容カードを重複と判定できなくなるため |
| シリアライズ順序 | 転記順のズレによる別ハッシュ化は当面許容。名寄せ・重複いずれかのマージの際に収束させる |

---

## 9. マージ処理時のルール

同一作品・同一キャラ・同一枝番で内容に差異があるカードが `03b_merge/` に送られた場合の処理手順。

1. 旧カード・新カードを比較リストに記録
2. 目視で各キーの採用値を選択し新カードを生成
3. `first_registered` は旧カードの値を引き継ぐ
4. `last_updated` は新カード生成日時に更新
5. 旧カードを mainDB から削除・インデックスから除去
6. 新カードを `src/app/03b_merge/M_Confirmed/` 送り dispatcher に再処理させる
7. 再処理では「該当なし」として `registercache/` 経由でADD登録
