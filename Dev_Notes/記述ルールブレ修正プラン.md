# 記述ルールのブレ確認と修正プラン（ラフ版）

## 1. 今回の確認範囲
- 対象: `src/app` 配下の `.php` / `.html` / `.json`
- 方針: 厳密な静的解析ではなく、運用で崩れやすいルール（改行・インデント・表記）を中心に確認

## 2. 観測したブレ（要点）

### A. インデント方針のブレ
- PHPは「スペース主体」のファイルが多い一方、タブを使うファイルも存在
- `archiver.php` ではタブとスペースが混在

### B. ファイル末尾改行のブレ
- 一部ファイルで final newline が欠落
- 対象拡張子を跨いで発生（PHP/HTML/JSON）

### C. 末尾スペース混入
- JSON/PHPで trailing whitespace が残っているファイルあり

### D. PHPヘッダ方針の未統一
- `declare(strict_types=1);` が現状のPHPファイルで未採用
- 命名規則（snake_case）や `<?php` 開始タグは比較的揃っているため、
  次は「strict_typesを採用するか否か」の方針決めが必要

## 3. 修正プラン（優先順）

### Phase 1: 低リスクの整形統一（先に実施）
1. final newline を全対象ファイルで統一（ありに統一）
2. trailing whitespace を一括除去
3. インデントを「4スペース」に寄せる（最低でも混在ファイルを解消）

> 目的: 振る舞いを変えず、差分ノイズを先に減らす

### Phase 2: PHPファイルの基本規約を定義
1. `strict_types` の採用可否を決定
2. 採用する場合は「新規ファイル必須」→「既存ファイルへ段階適用」の順で導入
3. 既存コードの暗黙型変換依存がないかを、処理単位で確認しながら適用

> 目的: 実行互換性を壊さない範囲で、将来の保守性を上げる

### Phase 3: 再発防止（自動チェック）
1. `.editorconfig` を追加（indent_style / indent_size / end_of_line / insert_final_newline / trim_trailing_whitespace）
2. pre-commit またはCIで軽量Lintを実行
   - 例: `php -l`（構文）
   - 例: 改行・末尾空白チェック（簡易スクリプト）
3. `README.md` か `Dev_Notes` に「最小コーディング規約」を明文化

## 4. 具体的な着手順（実作業ベース）
1. まず `.editorconfig` を作成
2. 既存ファイルに対して整形のみ一括適用（Phase 1）
3. まとめて `php -l` を実行して構文確認
4. 影響が出やすいバッチ系（normalizer/dispatcher/indexer）から順に動作確認
5. 最後に `strict_types` を段階導入（必要なら対象を限定）

## 5. 完了条件（このプランでの定義）
- 末尾改行・末尾空白・混在インデントの検出が0件
- 適用対象PHPで `php -l` が全件成功
- 規約ファイル（`.editorconfig` + 簡易ルール文書）がリポジトリに存在
