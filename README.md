# MZ-AniCharaDB

アニメ・キャラクター情報を **構造化JSONカード** として管理し、
正規化・重複判定・マージ・統計処理までを一貫して行うデータ管理基盤。

本システムは手作業入力・カードメーカー生成データの混在を前提とし、
運用現場での扱いやすさとデータ整合性の両立を目的としています。

------------------------------------------------------------------------

##   特徴

-   JSONカードによるキャラクタープロファイル管理
-   正規化処理による入力揺れ・破損データの自動補正
-   content_hash による重複判定
-   差分カードの **人手マージフロー**
-   ゲート制御による安全なバッチ処理パイプライン
-   将来の統計処理・名寄せ・分析に対応可能な構造

------------------------------------------------------------------------

##   処理フロー概要

    import → normalizer → dispatcher → index/register → archive → statistics

### フェーズ

1.  **Import**
    -   JSONカードを取り込み
2.  **Normalizer**
    -   スキーマ検証
    -   JSON正規化
    -   content_hash生成
    -   有効データ振り分け
3.  **Dispatcher**
    -   index.jsonと照合
    -   新規 / 重複 / 差分 を振り分け
4.  **Merge（人手）**
    -   差分カードの比較・統合
5.  **Indexer**
    -   DB登録・インデックス更新
6.  **Archive**
    -   原本保存

##   JSONカード仕様（概要）

### 必須フィールド

  フィールド   必須レベル
  ------------ ------------
  header       処理必須
  name         処理必須
  work         処理必須

### 推奨フィールド

-   profile
-   product
-   tags
-   rating
-   personality_parameters
-   comments

### 任意

-   extended
-   assets（将来用）

------------------------------------------------------------------------

##   header仕様

  フィールド         内容
  ------------------ -------------------------
  schema             スキーマ識別子
  uuid               アップローダー生成
  sid                セッションID
  content_hash       正規化時生成
  generated_at       生成日時（UTC ISO8601）
  first_registered   初回登録日時
  last_updated       更新日時

不一致スキーマは処理中断されます。

------------------------------------------------------------------------

##   personality_parameters 仕様

-   基本5軸
-   values 合計 = **10.0**
-   未評価時： `[5.0, 5.0]`
-   anchor は基準側インデックス

## ?? normalizer の役割

### 処理内容

-   スキーマ検証
-   JSON再構築（複製転記方式）
-   content_hash生成（MD5）
-   有効 / エラー振り分け

### 自動補正される問題

-   余分な引用符
-   スペース混入
-   カンマ抜け
-   インデント崩れ
-   不正キー末尾文字

### 処理対象外（名寄せフェーズ）

-   表記ゆれ
-   スペルミス
-   日英キー混在
-   意味的統合判断

------------------------------------------------------------------------

##   重複判定ロジック

### 判定基準

-   同一キー + 同一 content_hash → 完全重複
-   同一キー + 異なる hash → 差分カード（要マージ）

### content_hash仕様

-   MD5
-   headerを除外して算出
-   本文のみ対象

------------------------------------------------------------------------

##   マージフロー

差分カードは `03b_merge/` に送られます。

### 手順

1.  既存カードと新カードを比較
2.  採用値を選択
3.  新カード生成
4.  dispatcherへ再投入
5.  旧カードは OLD へ退避

------------------------------------------------------------------------

##   ゲート制御システム

本システムはゲートフラグにより各処理の実行可否を制御します。

### 主要ゲート

  ゲート             役割
  ------------------ ------------------
  receive            import成果物取得
  normalize          正規化成果物取得
  dispatch           振り分け処理
  dispatch_merge     マージ済み再処理
  archive            アーカイブ処理
  index_add          インデックス登録
  build_statistics   統計処理

------------------------------------------------------------------------

##   core.php の役割

-   cronから呼び出される制御モジュール
-   flock による多重起動防止
-   モジュールを順次実行
-   exitコードにより次工程制御
